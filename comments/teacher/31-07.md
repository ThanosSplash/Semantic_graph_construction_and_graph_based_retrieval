# Αξιολόγηση τρέχουσας κατάστασης και αναλυτικά επόμενα βήματα

Η υλοποίηση έχει πλέον:

- σωστότερο `nDCG@K`,
- graph-wide Personalized PageRank,
- cosine–PPR fusion,
- sensitivity grids για `alpha`, seed size (`init`) και graph construction,
- k-step neighborhood expansion,
- query-level αποθήκευση αποτελεσμάτων,
- graph statistics και leaderboard infrastructure.

Ωστόσο, πριν θεωρηθούν τα αποτελέσματα τελικά, παραμένουν θέματα σε:

- score calibration στο fusion,
- χειρισμό queries χωρίς retrieved relevant passage,
- καθαρισμό παλιών outputs,
- leaderboard/table formatting,
- evaluation sample,
- development/test protocol,
- reproducibility.

# 1. Τι έχει ολοκληρωθεί σωστά

## 1.1 Το `nDCG@K` έχει διορθωθεί

Η νέα υλοποίηση χρησιμοποιεί:

```python
ideal_len = min(len(correct_set), k)
ideal_y_true = np.ones(ideal_len)
```

Άρα το ideal DCG βασίζεται στο πλήθος των συνολικά relevant passages έως το `K` και όχι μόνο στα relevant passages που έτυχε να εμφανιστούν στο retrieved ranking.

Αυτό κλείνει το βασικό correctness issue της προηγούμενης υλοποίησης.

### Μικρή επιπλέον απαίτηση

Κράτησε toy tests για τουλάχιστον τις περιπτώσεις:

```text
1. Κανένα relevant στο top-K
2. Ένα relevant στην πρώτη θέση
3. Ένα relevant χαμηλά στο ranking
4. Πολλά relevant στο top-K
5. Περισσότερα relevant passages από το K
```

---

## 1.2 Το PPR + cosine fusion έχει υλοποιηθεί

Η υλοποίηση πλέον υπολογίζει Personalized PageRank για όλα τα nodes του γράφου και χρησιμοποιεί:

```python
score = alpha * sim_dict[node_id] + (1 - alpha) * graph_scores[node_id]
```

Άρα το PPR δεν περιορίζεται πλέον μόνο σε reranking των αρχικών seed passages. Μπορεί να αναδείξει νέα passages μέσω propagation στον γράφο.

## 1.3 Υπάρχει sensitivity infrastructure

Υπάρχουν πειραματικές μεταβλητές για:

- διαφορετικά `alpha`,
- διαφορετικά seed sizes (`init`),
- διαφορετικό αριθμό hops στο k-step,
- διαφορετικές κατασκευές γράφου,
- σύγκριση PPR με k-step.

Υπάρχει επίσης υποδομή για:

- PPR alpha-sensitivity tables,
- PPR init-sensitivity tables,
- graph-construction sensitivity table,
- global leaderboards,
- plots σύγκρισης PPR και k-step.

### Τι δεν είναι ακόμη πλήρες

Δεν φαίνεται να υπάρχει ακόμη ξεχωριστός, καθαρός πίνακας **hop sensitivity** για το k-step. Τα hops αποθηκεύονται στα runs και εμφανίζονται στο γενικό leaderboard, αλλά χρειάζεται ειδικός πίνακας:

```text
Graph | hops | init | alpha | Recall@K | MRR | nDCG@K | MAP@K
```

## 1.4 Υπάρχει query-level analysis

Αποθηκεύονται ανά query:

- predictions,
- recall,
- rank του πρώτου relevant passage,
- latency,
- relevant passage ids,
- query text.

Υπάρχει επίσης λογική σύγκρισης με το baseline:

```text
recall difference = graph_recall - baseline_recall
rank difference = baseline_rank - graph_rank
```

Η κατεύθυνση των διαφορών είναι σωστή όταν και οι δύο μέθοδοι έχουν βρει relevant passage.

### Σημαντικό bug στον χειρισμό αποτυχίας retrieval

Όταν δεν βρίσκεται relevant passage, το rank αποθηκεύεται ως `-1`. Στη σύγκριση μετατρέπεται σε `0`.

Αυτό αντιστρέφει τη σημασία της αποτυχίας:

```text
rank = 0
```

φαίνεται καλύτερο από:

```text
rank = 3
```

ενώ στην πραγματικότητα σημαίνει ότι δεν βρέθηκε κανένα relevant passage.

### Σωστή αντιμετώπιση

Για σύγκριση rank χρησιμοποίησε:

```python
missing_rank = k + 1
```

ή ένα σαφές μεγάλο sentinel.

Παράδειγμα:

```python
baseline_rank_cmp = baseline_rank if baseline_rank > 0 else k + 1
graph_rank_cmp = graph_rank if graph_rank > 0 else k + 1

rank_difference = baseline_rank_cmp - graph_rank_cmp
```

Άρα:

```text
θετική διαφορά → improvement
μηδενική → same
αρνητική → worse
```

Επίσης διόρθωσε το key:

```python
",relevant_passage_ids"
```

σε:

```python
"relevant_passage_ids"
```

# 2. Τι παραμένει μερικό ή προβληματικό

## 2.1 Λείπει το `alpha = 1.0`

Το τρέχον grid έχει:

```python
alphas = [0.0, 0.2, 0.5, 0.8]
```

Πρόσθεσε:

```python
alpha = 1.0
```

ώστε να υπάρχουν τα δύο καθαρά controls:

```text
alpha = 0.0 → μόνο PPR
alpha = 1.0 → μόνο cosine
```

---

## 2.2 Τα cosine και PPR scores δεν είναι στην ίδια κλίμακα

Αυτό είναι κρίσιμο για το fusion.

Το cosine score είναι συνήθως στην περιοχή:

```text
0 έως 1
```

Το PageRank score είναι πιθανότητα κατανεμημένη σε όλα τα nodes και συνήθως είναι πολύ μικρότερο.

Άρα στο:

```python
alpha * cosine + (1 - alpha) * PPR
```

το cosine μπορεί να κυριαρχεί σχεδόν πάντα, εκτός αν `alpha = 0`.

### Τι πρέπει να γίνει

Σύγκρινε τουλάχιστον:

```text
A. Raw-score fusion
B. Per-query min–max normalized fusion
C. Προαιρετικά rank-based fusion
```

Παράδειγμα:

```python
cos_norm = normalize(np.array(list(cos_scores.values())))
ppr_norm = normalize(np.array(list(ppr_scores.values())))
```

και μετά:

```python
final_score = alpha * cos_norm[node] + (1 - alpha) * ppr_norm[node]
```

Το normalized fusion πρέπει να γίνει η κύρια παραλλαγή ή τουλάχιστον υποχρεωτικό ablation.

---

## 2.3 Τα outputs μπορούν να συσσωρεύουν παλιά runs

Στο PPR υπάρχει:

```python
dt.clear_eval(file)
```

όμως το `clear_eval()` περιμένει πραγματικό file path.

Άρα πρέπει να χρησιμοποιείται:

```python
dt.clear_eval(f"Outputs/graphs/{file}/eval_results.json")
dt.clear_eval(f"Outputs/graphs/{file}/queries.json")
```

ή, ακόμη καλύτερα, κάθε experiment campaign να γράφει σε νέο run directory:

```text
Outputs/runs/<run_id>/
```

Στο k-step το clearing είναι σχολιασμένο, οπότε υπάρχει επίσης κίνδυνος ανάμειξης παλιών και νέων runs.

### Προτεινόμενη δομή

```text
Outputs/
  runs/
    2026-08-02_ppr_dev_v1/
      config.json
      aggregate_results.jsonl
      per_query_results.json
      tables/
      plots/
```

Μην χρησιμοποιήσεις leaderboard ως τελικό αποτέλεσμα αν δεν είσαι βέβαιος ότι περιέχει μόνο τα runs της συγκεκριμένης campaign.

## 2.4 Υπάρχουν bugs στα leaderboard tables

Το main leaderboard header περιέχει:

- `Density`,
- `Components`,
- δύο φορές `Recall`.

Όμως το row δεν γράφει density/components και γράφει μόνο ένα recall.

Άρα το header και το row δεν έχουν την ίδια δομή.

### Διόρθωση

Ή αφαίρεσε `Density` και `Components` από το γενικό retrieval leaderboard:

```text
Method | Recall | MRR | nDCG | MAP | Graph
```

ή πρόσθεσε πραγματικά τις τιμές στο row.

Στο graph sensitivity label για standalone threshold graph υπάρχει:

```python
graph = f"{graph_type} threshold = {neighbors}"
```

Πρέπει να είναι:

```python
graph = f"{graph_type} threshold = {threshold}"
```

## 2.5 Το υπάρχον query sample είναι μόνο debugging sample

Το sampling:

- κρατά περίπου το `2%` των επιλέξιμων queries,
- δεν κάνει shuffle,
- επιλέγει τα πρώτα queries κάθε κατηγορίας,
- αποκλείει queries με λιγότερα από 5 relevant passages.

Άρα είναι κατάλληλο για:

```text
debugging
pipeline validation
pilot runs
qualitative inspection
```

Δεν είναι κατάλληλο ως μοναδική βάση για το τελικό συμπέρασμα.

Ο ακριβής αριθμός των queries δεν προκύπτει μόνο από τον κώδικα και πρέπει να αναφέρεται από το generated sample/log.

### Διόρθωση

Για debugging:

```python
rng = np.random.default_rng(42)
```

και stratified random sampling ανά κατηγορία μήκους.

Για τα τελικά αποτελέσματα:

```text
χρησιμοποίησε όλα τα queries του frozen test set
```

Το φίλτρο `>=5 relevant passages` να χρησιμοποιηθεί μόνο ως ξεχωριστή subgroup analysis, όχι ως το κύριο result.

---

## 2.6 Δεν υπάρχει held-out evaluation protocol

Ο loader διαβάζει:

```text
question-answer-passages/train-...
text-corpus/train-...
```

Άρα τα graph parameters, `alpha`, `init`, hops και τελικά metrics επιλέγονται πάνω στο ίδιο query pool.

Αυτό δεν είναι training leakage νευρωνικού μοντέλου, αλλά είναι **hyperparameter-selection bias**.

### Σωστή διαδικασία

Αν υπάρχει official validation/test split:

```text
development queries → tuning
test queries → μία τελική αξιολόγηση
```

Αν δεν υπάρχει official split:

```text
1. Κράτησε σταθερό το corpus.
2. Χώρισε deterministic τα query ids σε development και test.
3. Χρησιμοποίησε μόνο development queries για επιλογή παραμέτρων.
4. Πάγωσε μία configuration.
5. Τρέξε το test set μία φορά.
```

Παράδειγμα:

```text
70% development queries
30% test queries
random seed = 42
```

Το corpus μπορεί να παραμείνει κοινό, επειδή το retrieval graph κατασκευάζεται χωρίς relevance-label training. Πρέπει όμως να δηλωθεί καθαρά ότι η αξιολόγηση είναι transductive ως προς το corpus.

## 2.7 Χρειάζεται reproducibility freeze

Το KMeans έχει:

```python
random_state = None
```

Για τα controlled experiments πρέπει να γίνει:

```python
random_state = 42
```

Για τα τελικά clustering-based αποτελέσματα:

```text

```

και να αναφερθούν:

```text
mean ± standard deviation
```

Η υποδομή ήδη αποθηκεύει αρκετές παραμέτρους, αλλά το τελικό run manifest πρέπει να περιλαμβάνει επιπλέον:

- dataset/split ids,
- embedding model,
- random seed,
- graph type και parameters,
- preprocessing,
- PPR `alpha`,
- seed size,
- `k`,
- hops,
- software versions,
- run timestamp,
- git commit, αν υπάρχει repository.

---

## 2.8 Χρειάζεται gold-coverage sanity check

Πριν από κάθε τελικό run έλεγξε ότι τα gold passage ids υπάρχουν στο corpus.

Αποθήκευσε:

```text
number of evaluation queries
total unique gold passage ids
gold ids present in corpus
gold ids missing from corpus
coverage percentage
queries with zero reachable gold passages
```

Αν λείπουν gold passages, το maximum achievable Recall είναι μικρότερο από 1 και πρέπει να αναφερθεί.

---

## 2.9 Καθόρισε με σαφήνεια το `MAP@K`

Η `avg_precision` διαιρεί με:

```python
len(correct_results)
```

Υπάρχουν διαφορετικές συμβάσεις για `AP@K`.

Πρέπει να δηλωθεί ρητά αν χρησιμοποιείς:

```text
denominator = total relevant documents
```

ή:

```text
denominator = min(total relevant documents, K)
```

Για να μπορεί να φτάσει το `AP@K` στο 1 όταν υπάρχουν περισσότερα από `K` relevant documents, συνήθως χρησιμοποιείται:

```python
min(len(correct_set), k)
```

Διάλεξε μία σύμβαση, πρόσθεσε toy tests και γράψ' την στην αναφορά.
